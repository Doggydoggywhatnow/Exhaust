# Exhaust 0.1.0: build spec

**Scope: everything in `README.md`, except its Non-goals.** Items marked *(later)* or *(optional)* are stubs: present in the interface where the README places them, clearly labeled, disabled, and documented as not yet working. Everything else must work.

Finish and commit each sub-slice, with its tests passing and CI green on Linux, Windows and macOS, before starting the next. Each sub-slice has a scope, the sub-slices it depends on, and one "done when" check that names a test or a command. Every parser sub-slice also adds its fuzz target (see `AGENTS.md`). A sub-slice that adds a dependency also updates `.github/workflows/ci.yml` for Linux, Windows and macOS.

**Size check between numbered slices:** after the last sub-slice of each numbered slice (5g, 6e-v, 7i, 8c) and before the first sub-slice of the next, build a Release install, run `tools/check_size.sh` on it (core limit 25 MB, which the CI job `size` also enforces on every push), and write the size and what each library added since the last check into `docs/PROGRESS.md` (rows marked **SIZE CHECK** between the slices) and the README's dependency table. The next numbered slice does not start while the install is over the budget: remove or replace what grew, or ask the owner to change the budget. There is no check between sub-slices of one number (5a and 5b, for example).

**Performance test vault:** `tools/gen_vault` (built in 2e) creates 5,000 notes with 20,000 links. All performance numbers below refer to it, on a 2020-era laptop.

**Names:** every setting key, theme token, file grammar and API name is defined in [`formats.md`](formats.md) before it is used. The sub-slice ids (such as 2a) are used in the traceability table at the end.

## 1a-i. Window, renderer and text atlas

Scope: SDL3 window; SDL_Renderer; FreeType glyph atlas; scalable text and HiDPI scaling. The skeleton's CI jobs (hardening flags, sanitizers, size budget) stay green on all three OSes.

Depends on: none (the skeleton)

**Done when:** `ctest -R renderer_smoke` passes on Linux, Windows and macOS in CI: with SDL's dummy video driver it renders glyphs from the atlas at 1x and 2x scale and matches stored images within a set tolerance.

## 1a-ii. Shaping, fonts, bidi, IME and clipboard

Scope: HarfBuzz shaping with font fallback and color emoji; system font scan of the OS font folders; SheenBidi for bidi and Exhaust's own UAX #29 segmenter for grapheme clusters (libgrapheme could not be vendored; see the README); SDL3 text input (IME); clipboard. The system font scan is cached in the OS cache folder, keyed by the modification times of the font folders, and fonts load lazily (only when a glyph needs them).

Depends on: 1a-i

**Done when:** `ctest -R shaping` passes: sample strings (Latin, Arabic, Hebrew, CJK, emoji, combining marks) give the expected glyph runs, bidi order and cluster boundaries, and the font scan finds at least one font. IME and clipboard cannot run unattended and are on the maintainer checklist. `ctest -R font_cache` passes: a second scan reads the cache, returns the same font list and does not scan the folders.


## 1a-iii. Buffer, undo tree and selections

Scope: Piece-table text buffer; undo tree; cursor, selection and multiple-cursor model. The edit stream can be serialized as journal records (format in `formats.md`) and replayed.

Depends on: none

**Done when:** `ctest -R buffer` passes, including a randomized test (fixed seed, 100,000 operations) against a simple reference buffer. `ctest -R journal_replay` passes: replaying the journal of a random edit sequence into a fresh buffer gives the same text.


## 1a-iv. Layout, widgets, theme tokens and editor widget

Scope: Clay layout and Exhaust's own widget tree; theme tokens (names in `formats.md`) loaded from the built-in light and dark token files, using the values in the Palette table in `formats.md`, with no hard-coded colors; an editor widget on the buffer; multi-cursor input. The message queue and worker-thread primitives: the UI thread never blocks on workers, workers send messages, and the UI reads snapshots.

Depends on: 1a-i, 1a-ii, 1a-iii

**Done when:** `ctest -R editor_widget` passes: scripted input types, selects, undoes and redoes multilingual text with several cursors under both token sets, and `ctest -R no_color_literals` fails if a color literal appears outside the token loader. `ctest -R worker_queue` passes: messages from several worker threads arrive in order for each worker, and the UI thread holds no lock that a worker holds.

Depends on: 1a-i

**Done when:** The CI job `a11y-build` builds the AccessKit static library with `cargo build --offline` on all three OSes, and the libFuzzer job runs its trivial target for 10 seconds without a crash.

## 2a. Vaults, file tree and file actions

Scope: Open and remember vaults; file explorer on the vault's real folders; in-app sorting by name, modified time or created time, ascending or descending. Sorting and grouping are done inside the app, stored in settings, and never rename, move or reorder anything on disk. Only create, rename, move and delete, which you do yourself, change files. Create, rename, move and delete with the trash modes (the file-trash functions for each OS in `src/platform/`); auto-reveal, expand and collapse all; the README's accepted file types; excluded files; symbolic links; the More-options menu items (open in default app, show in file manager, copy path). Backups need no code: the README states that any backup tool works.

Depends on: 1a-iv

**Done when:** `ctest -R vault_tree` passes: create, rename, move and delete work on a temporary vault in each trash mode, and changing the sort order leaves every file's path and modified time on disk unchanged.

## 2b. File watching, saving and note names

Scope: File watching (dmon or own code); autosave after a short idle; the conflict banner with a diff, keeping the editor's text when a file changes on disk during unsaved edits; CRLF, BOM and UTF-8 handling; note-name rules. Constant saving, as in the README's Saving bullet: an append-only recovery journal flushed within 200 ms (`journal_flush_ms`); atomic writes (a temporary file next to the note, flushed to disk, then renamed over it, keeping the symlink, permissions, line endings and BOM); autosave after 1 second idle (`autosave_idle_ms`) and at the latest every 5 seconds of continuous typing (`autosave_max_ms`); saving on focus loss, tab switch and window close; a flush on clean close, SIGTERM, SIGHUP, Windows session end and macOS terminate; after a crash, replay of the journal with a banner, and the conflict banner (keeping both versions) if the file changed on disk meanwhile; no file is created for a new note with nothing typed in it; on a write failure (disk full, permission denied, file locked) the text stays in the journal, a persistent error names the file, and the write is retried. File watching falls back to polling modification times every 2 seconds on a worker thread when the OS refuses more watches (inotify `ENOSPC` on Linux), says so in the status bar, and never watches excluded files.

Depends on: 2a

**Done when:** `ctest -R file_safety` passes: an outside edit updates the open buffer or raises the conflict banner when edits are unsaved, CRLF and a BOM survive a save byte for byte, invalid UTF-8 is refused, and every forbidden note name is rejected. `ctest -R autosave_crash` passes: a harness types text, kills the process with `kill -9` after 1 second, relaunches and finds all the text restored; `ctest -R write_failure` passes: a failing write keeps the text in the journal and reports the file name; and `ctest -R watch_fallback` passes: with a fake watcher backend that refuses watches, the polling fallback still detects an external edit.

## 4a-i. Index schema and indexer

Scope: SQLite index in the OS cache folder, keyed by vault, with numbered migrations and the `trigram` FTS5 tokenizer, plus tables for lines, blocks, sections and tasks; the indexer; rebuild from the notes. The trigram index is at most 4 times the size of the note text. SQLite runs in WAL mode with one writer connection (the indexer, on a worker thread) and one reader connection for each thread that needs one.

Depends on: 2b, 3a, 1a-iv

**Done when:** `ctest -R index` passes: the performance vault cold-indexes in under 10 seconds, a deleted index rebuilds to identical contents, and the index compatibility test (migration from every earlier schema version) passes. `ctest -R ui_not_blocked` passes: the longest UI frame while indexing the `tools/gen_vault` vault has under 16 ms of blocked time; and `ctest -R index_size` passes: on that vault the trigram index is at most 4 times the size of the note text, and the test prints the ratio.

Depends on: 4a-i, 3a

## 5a. Barnes-Hut layout and graph rendering

Scope: Force-directed graph with Barnes-Hut layout; rendering with the tessellator (nodes sized by links, lines, labels, hover highlight, click to open, pan and zoom). The whole graph is batched into one geometry buffer per frame, off-screen items are culled, labels are hidden when zoomed out below a threshold, and the Barnes-Hut layout runs on a worker thread while the UI draws the latest snapshot.

*Opening the graph:* the ribbon's graph button (disabled until now) and the command `graph-view.open-graph-view` (`Ctrl+G`, also in the command palette) open a tab with the view `graph` in the active group, or bring the graph tab to the front when one is already open (a second graph is made by splitting or by the local graph in 5c); the `graph` feature switch hides the button and the command; a session with a graph tab restores the tab (pan and zoom are not saved; `[graph]` keys come with 5b's settings); opening a graph bookmark (4b-iv) is not built in 5a (see `PROGRESS.md`). The note that is open in the main text view is drawn in the focus color. Keys (built): arrow keys pan, `+` and `-` zoom, `0` or Home fits the graph, Page Down and Page Up step through the nodes, Enter opens the selected node, Escape clears the selection; the full keyboard list is in 5c. *Hover and right-click:* hovering a node shows the page preview of its note (needs Ctrl as `[page_preview] ctrl_required_graph` says; the preview is the one of 4c and 4d, asked of the service thread, never read on the UI thread); a right-click on a note's node opens the same popup menu a note has in the file explorer (4d: open in new tab, make a copy, move, bookmark, copy path, open in default app, show in file manager, rename, delete), as built; an unresolved node offers *Create note* (changed on building 5a: this replaces the list *Open*, *Open in new tab*, *Open to the right*, *Reveal in file explorer*, *Copy link* written first, so that a node and a note in the explorer have one menu; the entries that were not there come with 5d and 5e). Only the graph itself is built here: the pane header, the gear and the wand are in 5b, 5c and 5d.

Depends on: 4a-ii, 1a-i

**Done when:** `ctest -R graph_data` passes: the graph's data (every note, attachments, unresolved names shared by every link to them, one edge for repeated links, none for a link to the note itself) is right on a small vault, and on the performance vault (5,000 notes, 20,000 links) the counts are right and the index is asked at most once for each link. `ctest -R graph_perf` passes on a graph of the performance vault's size (5,000 nodes, 20,000 edges, made in the test). It measures work, not wall-clock frames per second (`AGENTS.md` forbids that on slow runners; this replaces the earlier wording "at least 30 frames per second", changed 2026-11-15): Barnes-Hut does at least 5 times fewer repulsion terms per step than all pairs, its forces are within 5% of the exact forces, the layout settles in 250 to 400 steps, linked nodes end up closer than random pairs, a copy the UI side reads is never torn while the worker writes, a changed graph starts where the old one was, the same seed gives the same picture, and a running layout can be stopped. `ctest -R graph_frame` passes: for the same size, with the layout running, the time of a frame's own code (the widget layout, choosing what is on screen, building the geometry buffer and handing it to the renderer) is within the limits of `frame_budget` at three zoom levels (95th percentile; ten times that under sanitizers), the triangles handed over stay under 120,000, nothing is allocated in a steady frame, only what is on screen is drawn, labels appear only zoomed in, and an input handler takes under 16 ms while the layout runs. **What it does not limit:** SDL's software rasterizer drawing those triangles (0.1 to 0.5 seconds a frame in a build without optimization here); it is printed, not limited, because it is not our code and the real renderer is a GPU (decided on building 5a; `frame_budget` charges the rasterizer, which is right for text, where the same queue is flushed by the glyph atlas). The tessellator has its own test (`render_geometry`).

## 5g. Dragging nodes and the link force

Scope: (1) **Dragging nodes in the graph** (added 2026-11-15 at the owner's request; 5a left it out). Pressing on a node and moving the pointer drags it. **Decided 2026-11-15 by the owner: the node goes towards where you drag it, but it is still pulled by the other forces (its links, the repulsion, the centre pull) back to an area that works with the forces.** So it is not pinned to the pointer: the pointer pulls the node with a strong spring (a force on that one node, stronger than the others but finite, so a node dragged far away is pulled back by its links as soon as the pointer stops pulling), the layout keeps running and the other nodes follow through their links, and on release the node settles where the forces put it (usually near where it was let go if that is a place the forces accept, and back in the cluster if not). A press that does not move is still a click that opens the note; a press on empty space still pans. The layout gets the pin through the same lock-free route as the forces (a message or atomics: the UI thread never waits for the layout), the pointer's position in layout units is the target of the pull on the dragged node, the layout wakes while a node is dragged, and the hover, the selection and the page preview keep working. Keyboard: a way to move the selected node (for example Alt with the arrow keys). (2) **The link force slider must do something you can see.** In the real program (5b's AppImage) moving the *Link force* slider showed no visible change; the test `graph_options` shows strength 0 against 1 changes the mean link length (47 against 443 layout units on a ring), so the cause is somewhere between that and the user's hand: check the range (springs are scaled by one over the smaller degree, so most of the slider's range may be too weak to see), whether the layout is woken and restarts hot enough, and whether a settled picture is already at rest. Make the whole range of the slider matter (a different curve or scale, written into `formats.md` first, with the default keeping 5a's picture), and check by screenshot at three values. (3) **Zooming in deeper, with the text growing** (added 2026-11-15 at the owner's request). Today the view stops at a zoom of 8 (`ZOOM_MAX` in `src/ui/graphview.c`) and labels stay one size however close you are. Raise the limit a lot (a few dozen times today's, chosen by looking at a screenshot of two linked nodes filling the view) and let the labels grow as you zoom in past the point where they appear, so a note's name is as large as the circle it belongs to; the growth is capped (the same cap for the width the label may take, `ex_text_fit`) so a label never fills the pane, and the nodes' circles grow with the zoom too. The wheel and the `+` and `-` keys reach the new limit, and a fitted view (`0`) still works. The label size multiplier is the place to add the owner's earlier wish for a text size option (ISSUES 34); if it is cheap, add the option here too. The cost of a frame must not grow: at the deepest zoom only a few nodes are on screen, and the existing culling and label caps keep it that way.

Depends on: 5b
